# Interface Quality Rubric

Use this rubric to test whether an interface contract is product-specific and implementation-ready. Do not convert it into a numeric score.

## Contents

- Product legibility
- Workflow fit
- Hierarchy and density
- Visual system
- State completeness
- Responsive behavior
- Accessibility
- Performance and feasibility

## Product Legibility

Confirm that a first-time user can determine:

- what object or activity the product centres on;
- what status or decision matters now;
- what the primary action will do;
- which information is real content rather than decoration.

Reject product-agnostic headings, statistics, cards, or illustrations that occupy the first viewport without helping the primary job.

## Workflow Fit

Choose patterns from the work:

- tables for dense comparison and repeated operations;
- timelines for sequence and time relationships;
- editors or canvases for direct manipulation;
- forms for deliberate data entry;
- feeds for recency and ongoing activity;
- dashboards only when simultaneous monitoring is truly the job.

Avoid converting every application into equal-weight cards.

## Hierarchy and Density

Verify that visual weight follows decision importance, controls sit near affected objects, frequent actions remain reachable, destructive actions are protected, and whitespace separates meaning.

## Visual System

Require semantic roles rather than isolated values:

- background, surface, and raised surface;
- primary and secondary text;
- quiet and strong borders;
- accent, success, warning, danger, and focus;
- display, section, body, label, data, and code typography roles.

Use one clear spacing rhythm and a restrained surface vocabulary. Distinctiveness should come from product content, hierarchy, interaction, type, imagery, and data treatment before decoration.

## State Completeness

Consider first use, loading, empty with a useful next action, partial data, success, validation, recoverable error, unavailable or disconnected state, disabled and why, selection, focus, and destructive aftermath. Do not invent states that cannot occur.

## Responsive Behavior

Specify:

- what remains visible;
- what becomes a menu or sheet;
- what scrolls intentionally;
- what changes order or representation;
- what remains reachable with one hand;
- how keyboard and pointer use differ.

Stacking every desktop region vertically is not a responsive strategy.

## Accessibility

Require semantic controls and landmarks, visible focus, logical reading and tab order, associated labels and errors, non-colour cues, sufficient contrast, zoom resilience, reduced-motion behavior, and correct focus placement and return.

Do not claim assistive-technology compatibility without actual testing.

## Performance and Feasibility

Check that the interface fits the existing stack, avoids heavy media without benefit, defines loading for slow operations, remains usable with representative data, and has a fallback when advanced presentation fails.
